# 06: Split the asset logic from the Yew page

Status: ready-for-agent
Blocked by: None (can start immediately)
Spec: `.scratch/docs-overhaul/spec.md`

**What to build:** The parts of `src/wasm/yew_ui/model.rs` that do not need Yew
move into a module outside `yew_ui/`. These parts are:

- the state of each asset in the hub cache and in memory,
- the plan of the download chunks,
- the wrapper builder.

A future web front-end can then use them. The Yew page keeps only its messages,
its reducer and its view.

## Questions for the triage

- The name and the place of the new module, for example `src/wasm/assets.rs`.
- Is the module free of `web-sys` too, so that a test can run it natively?

### Triage answers

- The new module is `crate::common::assets`. It is free of Yew and of
  `web-sys`, so a native `cargo test` runs its tests.
- The module holds the state changes of the assets, not only their types.
- The term "plan" goes to `GLOSSARY.md`. This ticket renames the identifiers
  that use the term.
- The items that no code uses stay. The maintainer plans to implement them
  later.

## Agent Brief

**Category:** enhancement

**Summary:** Move the asset logic of the browser page into
`crate::common::assets`, a module without Yew and without `web-sys`. Then
native tests can run it, and a future web front-end can use it.

**Current behavior:**

- The state module of the Yew page holds `Model` and these items: `Asset`,
  `AssetKind`, `AssetConfig`, `HuggingfaceConfig`, `CustomConfig`, `Load`,
  `HubCacheState`, `FetchState`, `MambaWrapperBuilder`, `Wrapper` and
  `Connection<T>`. Only `Model` needs the `yew` feature, for its
  `gloo_timers` interval.
- The reducer (`Model::update`) changes the asset state inline, between its
  calls to `ctx.link()`.
- The methods `api_repo`, `metadata` and `check` of `AssetConfig` and
  `HuggingfaceConfig` take the wasm hub client `Api`.
- `DownloadChunkKey` and `DownloadChunkList` are in the wasm hub client. That
  module compiles only for wasm.
- `ApiRepo::check` reads the cached download chunks from IndexedDB, then walks
  them to make the plan. No test covers the walk.
- `Model::default` and `MambaWrapperBuilder::default` read the preferred
  checkpoint from `hf::preferred()` themselves.
- No test covers the browser page or the browser console.

**Desired behavior:**

1. `crate::common::assets` compiles with each family feature (as `store_load`
   does), on each target. It holds the items of the list above, except
   `Model`. Each item keeps its behavior.
2. The methods of `AssetConfig` and `HuggingfaceConfig` that take `Api`
   compile only for wasm. `file_url` and `file_path` compile on each target.
3. A new type `Assets` holds the two assets of one checkpoint, the wrapper
   builder and the run wrapper (`Option<Wrapper>`). The Yew `Model` holds one
   `Assets` in place of these four fields.
4. The state changes of the reducer become methods of `Asset` and `Assets`.
   The reducer calls these methods. It keeps only the messages, the futures,
   the view state and the generation. The methods keep these rules:
   - A finished check stores the metadata and the plan. It marks the hub
     cache state as done only when the hub cache holds each download chunk
     of the plan.
   - A fetched download chunk becomes a cached entry of the plan. The
     progress count increases by one.
   - A failed fetch and a finished fetch end the busy state.
   - A load collects the keys of the plan. It panics when the hub cache does
     not hold a download chunk, as now.
   - A finished erase marks each download chunk of the plan as not cached.
   - A failed erase puts the asset back into the check state.
   - An unload with a run wrapper drops the run wrapper, and marks both
     assets as not loaded.
   - An unload without a run wrapper frees only the built part and the loaded
     bytes of its asset.
   - A build gives the loaded bytes of the asset to the wrapper builder. When
     the builder holds the tokenizer and the network, `Assets` makes the run
     wrapper.
5. The page gives the checkpoint spec to `Assets`. No item of the module
   calls `hf::preferred()`.
6. After `Assets` makes the run wrapper, a new wrapper builder for the same
   spec replaces the old one. So a load after an unload builds again.
7. The rename for the term "plan" of the glossary:
   - `DownloadChunkList` becomes `DownloadChunkPlan`.
   - Each `download_chunk_list` field or variable becomes `plan`.
8. `DownloadChunkKey` and `DownloadChunkPlan` move to the shared types of
   `crate::hub`. They compile on each target.
9. A pure function `plan_download_chunks` holds the walk of `ApiRepo::check`.
   `ApiRepo::check` reads IndexedDB, then calls it.
10. `web-time` is a dependency on each target. Natively, it is `std::time`.
11. These items stay, with their docs: `AssetConfig::Custom`,
    `CustomConfig`, `Connection::Disconnecting`, `MambaWrapperBuilder::merge`
    and the `Msg` variants that the page does not implement.

**Key interfaces:**

- `Assets::new(spec: &'static CheckpointSpec)`: makes the two assets from the
  spec, as `Model::default` does now. `select(kind)` and `select_mut(kind)`
  move from `Model` to `Assets`.
- `MambaWrapperBuilder::new(spec)`: replaces the `Default` impl of the
  builder, because a default can not know the spec.
- `plan_download_chunks(blob_prefix, size, download_chunk_len, cached) ->
  DownloadChunkPlan`: `cached` holds the cached keys of one blob, in
  ascending offset order. The function ignores a cached key of length zero.
- `DownloadChunkKey::new` and `DownloadChunkKey::parse`: visible to the wasm
  hub client and to the tests. A native build gives no dead-code warning.

**Acceptance criteria:**

- [ ] The Yew page imports each moved item from `crate::common::assets`. Its
      state module holds only `Model` and its `Default` impl.
- [ ] On a native target, the module and the shared hub types need no
      `yew`, `gloo-timers`, `web-sys`, `js-sys` or `indexed_db_futures`.
- [ ] `rg 'preferred\(' src/common/assets.rs` finds no match.
- [ ] `rg -i 'download_?chunk_?list'` finds no match in the repo, the
      `.scratch/` tracker excluded.
- [ ] Native tests of `plan_download_chunks`. In each test, the entries of the
      plan are contiguous from offset 0 to the file size:
  - An empty hub cache gives only entries to fetch, each of the download
    chunk length. The last entry ends at the file size.
  - A full hub cache gives only cached entries.
  - Cached keys of another download chunk length give a valid plan.
  - A cached key that starts inside a gap ends the entry to fetch before it
    at its start.
  - A file of size zero gives an empty plan.
  - A cached key of length zero has no effect on the plan.
- [ ] Native tests of the state methods: one test or more for each rule of
      point 4. The tests need no weights file and no tokenizer file.
- [ ] `scripts/check.sh` passes, and runs the new tests.
- [ ] The docs follow, in the style of `asd-ste100`:
  - The header of the new module describes the asset lifecycle. That text
    moves from the header of the Yew page.
  - The header of the Yew page names only its messages, its reducer and its
    view.
  - The header of `crate::hub` names the download chunk types as shared
    types.
  - The File Map of `CLAUDE.md` has a line for `assets.rs`. The line tells
    that only the browser front-ends use it.
  - `docs/agents/testing.md` has a row for the new seam. Its "Outside the
    seams" section says that only the asset logic of the browser page has
    tests.
- [ ] These stay the same: the IndexedDB names and the key layout, the page
      labels, the `Msg` variants and the behavior of the page.
- [ ] The user runs the page in the browser before the ticket closes: check,
      fetch, load, generate, unload, load again and erase.

**Out of scope:**

- The generation in the reducer: start, step, stop, resume and the reset of
  the caches.
- The browser console. It keeps its own `build_wrapper`.
- A run-time pick of the checkpoint (ticket 07).
- An implementation of the custom source, the disconnect or the upload.
- A change in `../burn-mamba`.
- A bench gate. The change does not touch the timed code.
